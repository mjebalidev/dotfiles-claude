# Global instructions

How replies are formatted lives in the `Pro` output style. This file covers
how the work itself is done.

## Code

- Simplest thing that works. No abstraction for a single call site.
- Read a file before editing it. Follow the surrounding style over any
  general convention.
- Comments say *why*, never what. No `Added by`, `Updated by`, no dated notes.
- No docstrings or type hints on code the change does not touch.

## Commits

Angular format, enforced by the `commit-msg` hook:

```
<type>(<scope>): <subject>

<body: why, not what>
```

- Types: `build` `chore` `ci` `docs` `feat` `fix` `perf` `refactor` `test` `revert`.
- Subject: imperative, lowercase first letter, no trailing period, 72 chars max.
- Scope optional, lowercase (`[a-z0-9._/-]`).
- Breaking change: `!` after the scope **and** a `BREAKING CHANGE:` footer.
- One commit per logical change. Split by subject, not by file.
- Never `--no-verify`.

I am the author and answer for every commit. When an agent wrote or shaped
the change, the commit says so in one trailer, last:
`Assisted-by: <tool>:<model>` (`Assisted-by: claude-code:claude-opus-5-5`).
Nothing else: no `Co-Authored-By` for an agent, no `Signed-off-by` on my
behalf, no `Generated with`, no `Claude-Session:`, no AI in branch names or
code. A client's own rules win over this one, in either direction.

PR descriptions state the user-visible change and the why, and end with the
same `Assisted-by:` line when it applies. The diff already lists the files.

## Language

Everything written to a repo is in English: code, comments, commits, docs,
instructions. Replies follow the language I write in.

## Documentation

README: what, why, getting started in under 5 commands; the rest in `docs/`.
Everything else: the `doc-writer` skill.

## Tone

Write like a person. No "It's important to note", no "not X, but Y" reflex,
no rule-of-three padding, no em dash inflation, no significance claims
("underscores", "represents a shift"). State the specific thing and stop.
Details: the `humanizer` skill.

## Tools

Installed and preferred where they fit: `ast-grep` for structural search and
rewrites, `difft` to read a diff, `kubeconform` to validate manifests offline.
`gcloud`, `glab`, `kubectl`, `helm`, `flux`, `argocd`, `tofu`, `terragrunt` and
`vault` are for reading; mutations go through IaC or CI.

## Clusters and cloud accounts

Client work lives under `~/Projects/<client>/`. direnv sets `KUBECONFIG`,
`CLOUDSDK_ACTIVE_CONFIG_NAME` and `GOOGLE_APPLICATION_CREDENTIALS` for that
client, so a session started elsewhere sees another client's clusters or none.

- If `KUBECONFIG` is unset, or is not the path the folder's `.envrc` exports
  (after `kx`, a `kx.*/config` copy whose `base` file holds that path), stop
  and say so before any `kubectl`, `helm`, `flux`, `gcloud` or `tofu` command.
- Client kubeconfigs have no current-context: pass `--context` on every call.
  Contexts are `<client>-<env>-<role>`; `-prod-` means production.
- `~/.kube/configs/` is generated by `kube-sync <client>` from
  `~/.config/kube/clusters.d/`. Change the inventory and re-run it; never
  write into those files with `get-credentials` or by hand.

## Where a piece of knowledge goes

Decide who may read a fact before writing it down. This repo is public: no
employer or client name, project ID, hostname, endpoint or account goes in it;
those live in private repos, and secrets in none.

## Delegation

Do the work inline by default, edits to `.tf`, manifests and code included. A
subagent earns its cost for parallel work, for long output that should stay
out of this conversation, or for a reviewer that has not seen the reasoning:

- `code-reviewer`: a finished change in Python or TypeScript, before the MR.
- `incident-responder`: something broken in production.
- `iac-engineer`, `k8s-gitops-engineer`, `ai-platform-engineer`: a large,
  self-contained piece of work in their domain that can run while I continue.
